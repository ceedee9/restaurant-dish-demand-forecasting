Part 1 — ML Workflow (Model Development)

Data preprocessing → training → evaluation → selection
~5 min
1.1 — Problem Statement
Say This

"Our task is a supervised regression problem. Given the dish name, day of the week, weather condition, whether it is a Philippine public holiday, and date information — we predict quantity_sold: how many servings the restaurant will sell that lunch period. After one-hot encoding, the model receives 30 input features per row."

1.2 — Data Preprocessing
Say This

"We applied a 7-step preprocessing pipeline inside train_and_save.py. The key design decisions were:"

  • Loading and combining both Excel files with pd.concat() — giving 509 rows.
  • Extracting month, day_of_month, week_of_month from the date column to give the model temporal patterns.
  • Dropping meal_period (all rows = "Lunch") — zero variance, teaches nothing.
  • One-hot encoding: 16 dish columns + 7 day columns + 3 weather columns.
  • Fitting the StandardScaler only on X_train to prevent data leakage.
  • 70/30 train-test split with random_state=42 for reproducibility.
⚠️ Data Leakage — Anticipated Question
We fit the scaler exclusively on X_train, then transform both X_train and X_test. Fitting on all data would let test statistics "leak" into training — inflating scores.
1.3 — Algorithm Selection (7 Models)
Say This

"We did not just pick one algorithm. We compared seven, ranging from simple linear models to ensemble methods — to have an evidence-based selection rather than a guess."

Model Type Why Included

Ridge Regression Linear + L2 Handles correlated one-hot features
Lasso Regression Linear + L1 Can zero out irrelevant columns

Our R² values are negative, which means the model performs worse than a simple mean predictor on the test set. This is a realistic outcome with only 2 months of data (509 rows) across 16 dish types. 1.6 — Cross-Validation
Say This

"We ran 10-Fold Cross-Validation on all 7 models to check generalization — not just test set performance. Random Forest showed the lowest R² standard deviation (±0.125), making it the most stable model. Lasso was most stable numerically but also weakest."

3.2 — Step-by-Step Data Flow (10 steps)
Say This

"Walk through what happens from click to prediction:"

  1. User selects dish, day, weather, holiday flag, and date, then clicks Predict.
  2. Browser sends a POST /predict HTTP request with a JSON payload to http://127.0.0.1:8000.
  3. app.py validates dish name, day, and weather against the known valid lists — returns HTTP 422 if invalid.
  4. Feature engineering — builds a one-hot encoded single-row dictionary matching the 30-column training structure.
  5. Column alignment — pd.DataFrame.reindex(columns=feature_cols, fill_value=0) ensures exact column order.
  6. Scaling — applies scaler.transform() using the saved StandardScaler from training.
  7. Prediction — model.predict() returns a raw float (e.g., 21.4 servings).
  8. Rounding — max(1, round(float(prediction))) gives a practical integer ≥ 1.
  9. API responds with JSON containing servings count, recommendation text, and model info.
  10. Frontend displays the servings number and recommendation to the staff.

Q&A Preparation

Anticipated instructor questions and suggested answers
Q: Why are your R² scores negative?

"Negative R² means the model is worse than a baseline mean predictor on the test set. This is a data limitation — we only have 2 months (509 rows) spread across 16 dishes. Each dish has roughly 32 training rows on average, which is not enough for a regression model to capture reliable patterns. Our learning curve shows the validation score is still improving at full data size, which confirms that more training data — at least 6 months — would significantly improve performance. The system architecture and integration are complete and production-ready."

Q: Why did you choose Gradient Boosting / Random Forest as the final model?

"We selected the model with the best optimized test R² at runtime. Among baseline models, Gradient Boosting had the least negative R² (−0.100 vs −0.152 for Random Forest), and after Grid Search both improved. We selected based on five criteria: highest R², lowest MAE, CV stability, ensemble method robustness, and restaurant applicability."

Q: What is data leakage and how did you prevent it?

"Data leakage is when information from the test set influences model training, making scores appear better than they would be on truly unseen data. We prevented it by fitting the StandardScaler exclusively on X_train, then using scaler.transform() on both X_train and X_test — never scaler.fit() on X_test."

Q: What does the /predict-batch endpoint do?

"It accepts a list of dish-day-weather combinations and returns predictions for all of them in one request. This is designed for morning planning — the restaurant manager can submit all 16 dishes for a given day and get the full daily prep list in one API call."

Q: What would you improve with more time?

"Three improvements: (1) Collect more data — ideally 6–12 months to give the model enough variety per dish. (2) Add more features like nearby events or promotions. (3) Retrain the model weekly with new sales data so it adapts to changing demand patterns."

Q: How is the model saved and loaded?

"We use joblib.dump() to serialize the trained model object to a .pkl file. At web server startup, app.py calls joblib.load() to restore it into memory — this happens once. All subsequent prediction requests reuse the same in-memory model object, so there is no file I/O per request."

Q: Why use FastAPI instead of Flask?

"FastAPI provides automatic input validation via Pydantic models, auto-generated Swagger documentation at /docs, and is significantly faster than Flask for I/O-bound workloads. It also enforces type hints, which catches input errors before they reach the model."
